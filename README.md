# Event Registration — Camunda 8 Process + Linked Form

A simple **Event Registration** process modeled in Camunda Modeler for Camunda 8 (Zeebe),
with a Camunda Form linked to its User Task. It covers the full assignment flow:
**model → form → link → deploy → run → verify**.

![Event Registration process diagram](diagrams/bpmn_diagram.png)

## The process

A candidate registers for an event. The process checks seat availability. If a seat is free it
calculates the fee, confirms the registration, prints a badge and emails a confirmation.
Otherwise it notifies the registrant that the event is full.

| Element | Type | What it does |
|---|---|---|
| Fill Registration Form | **User Task** | Human fills the linked form in Tasklist |
| Check Seat Availability | **Service Task** | Job type `check-seat-availability`, returns `seatsAvailable` |
| Seats Available? | Exclusive Gateway | `YES` if `seatsAvailable = true`; **`NO` is the default flow** |
| Determine Registration Fee | **Business Rule Task** | Calls DMN decision `registrationFee` → variable `fee` |
| Confirm Registration | **Service Task** | Job type `confirm-registration`, returns `confirmationNumber` |
| Print Visitor Badge | **Manual Task** | Documents a human step; Zeebe passes through it automatically |
| Send Confirmation Email | **Send Task** | Job type `send-confirmation-email` |
| Notify: Event Full | **Service Task** | Job type `notify-registrant` |

Fee rules (DMN): Student = 10, Professional = 50, Guest = 25.

## The form and how it is linked

`models/event-registration-form.form` has the form `id` **`event_registration_form`**. The User Task
points to it with:

```xml
<zeebe:formDefinition formId="event_registration_form" bindingType="latest" />
```

That matching ID is what links the two. Deploy the form together with the process.

| Label | Key | Type | Validation |
|---|---|---|---|
| Full Name | `fullName` | text field | required |
| Email Address | `email` | text field | required, email format |
| Event Date | `eventDate` | date | required |
| Registration Category | `category` | select (Student / Professional / Guest) | required |
| Reason for Attending | `reason` | text area | required, min 10 chars |
| I agree to the event terms | `agreeTerms` | checkbox | must be ticked |

Each field has its own key, so each becomes its own process variable on completion.

## How to run it end to end

1. **Open** `models/event-registration.bpmn` in Camunda Modeler (Desktop or Web Modeler).
2. **Deploy** all three files together (DMN, form, BPMN) using the **Deploy** button, connected to
   your Camunda 8 cluster (SaaS or self-managed).
3. **Start an instance** of `Process_EventRegistration` (Modeler's *Start instance*, or from Operate).
4. **Open Tasklist** → *Fill Registration Form* → **Claim** → fill all six fields → **Complete**.
5. **Open Operate** → open the process instance → **Variables** tab.

### What you should see in Operate

| Variable | Example |
|---|---|
| `fullName` | `"Asha Kumar"` |
| `email` | `"asha@example.com"` |
| `eventDate` | `"2026-11-15"` |
| `category` | `"Student"` |
| `reason` | `"I want to learn about workflow automation."` |
| `agreeTerms` | `true` |

The form values appear immediately after you complete the task. The token then waits at
**Check Seat Availability** because no job worker is running. That is expected and is enough for
this assignment. `seatsAvailable`, `fee` and `confirmationNumber` only appear if you also run
workers for the four job types above (`check-seat-availability`, `confirm-registration`,
`send-confirmation-email`, `notify-registrant`).
